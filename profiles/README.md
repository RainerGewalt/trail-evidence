# Profile registry

A profile defines the payload of one kind of record. Trail Evidence defines
the shared structure (canonicalisation, chaining, versioning); a producer
defines its domain data as a profile and registers it here. A record names
its profile in the core member `profile`, for example
`"profile":"example.measurement/1"`. `SPEC.md` section 3.4 is normative;
this file describes the registry and how to submit a profile.

The registry holds one profile so far, `example.measurement/1`. It is a test
profile: it exists to exercise the verifiers and to show what a submission
contains. Producers register their own profiles; a broker profile, for
example, is defined by the broker's producer, not in this repository.

## Layout

```
profiles/
  <name>/
    <major>.schema.json     the payload schema (required)
    <major>.examples.json   payloads a verifier must accept and reject (required)
    <major>.journal.jsonl   records written by the producer's implementation (required)
```

The verifiers read copies of the schemas: `go/evidence/profiles/` (embedded
with `go:embed`), `python/trail_evidence/profiles/` (package data) and
`web/profiles.js`. `scripts/profiles.py --write` generates them from this
directory; never edit a copy. `scripts/profiles.py --check` checks the rules
below and fails when a copy is stale, and so do the tests of each verifier.

## Rules

**Identifier.** `<name>/<major>`. The name matches
`^[a-z][a-z0-9]*(\.[a-z][a-z0-9_]*)+$`: lowercase, at least two segments,
the first identifying the producer or its organisation (for example
`acme.batch_record`). The major version is an integer from 1 without
leading zeros.

**Versions.** Only the major version is part of the identifier. Within a
major, a new minor version may add optional members and nothing else: no
new required member, no removed member, no changed type or meaning. Every
other change is a new major, registered as a new `<major>.schema.json` next
to the old one, which stays. A producer that wants to record its minor
version puts it into the payload; verifiers ignore it.

**Schema.** JSON Schema 2020-12 with:

- `"$schema": "https://json-schema.org/draft/2020-12/schema"`,
  `"title"` equal to the identifier, a `"description"`, and
  `"type": "object"` at the top level;
- only the keywords `type` (one type name or an array of them), `required`,
  `properties` and `items` (one schema for every element), plus the
  annotations `$id`, `$comment`, `description` and `examples`.

There is no `additionalProperties`, `enum`, `pattern`, `minimum` or
`format`: a profile checks that the required members are present and that
members have the declared types, and allows members it does not name, so
that payloads of a later minor version still pass. The keywords have their
JSON Schema meaning (`integer` is a number without a fractional part, so
`16.0` counts). Values whose exact rendering matters, such as measurements,
amounts and probabilities, are strings (`SPEC.md` section 4.3).

**Examples.** `<major>.examples.json`:

```json
{
  "profile": "<name>/<major>",
  "note": "…",
  "valid":   [ { "description": "…", "payload": { … } } ],
  "invalid": [ { "description": "…", "payload": { … } } ]
}
```

At least one valid and one invalid payload; in practice one invalid payload
per required member and per typed member, and one valid payload with a
member the schema does not name. Every verifier must accept each `valid`
payload and reject each `invalid` one; `scripts/profiles.py` also checks
them with a full JSON Schema validator when the `jsonschema` package is
installed.

**Journal.** `<major>.journal.jsonl` is written by the producer's own
implementation, not by hand and not by this repository's code: it is the
evidence that an independent producer and the verifiers here agree. Every
record carries the profile; the journal must verify with `--strict` in Go,
Python and the browser verifier, every record `valid` with profile state
`valid`. A few records are enough. The journal of `example.measurement/1` is
generated by the Go reference implementation, because that profile has no
other producer.

## Submitting a profile

1. Open an issue that names the producer, the identifier and what one
   record represents.
2. Add the three files under `profiles/<name>/`, run
   `scripts/profiles.py --write`, and commit the files together with the
   generated copies.
3. Run the checks from `CONTRIBUTING.md`; `scripts/crosscheck.sh` verifies
   the journal with all three verifiers and compares their reports.
4. Add a line to `CHANGELOG.md`.

A registered major version keeps its meaning. Within it, a pull request may
only add optional members to the schema, with examples for them.

## What a verifier reports

| Record | Profile state | Finding |
|---|---|---|
| no `profile` member | `none` | – |
| known profile, payload satisfies it | `valid` | – |
| known profile, payload violates it | `invalid` | `profile_invalid` (error; the record is `invalid`) |
| `profile` malformed, for example `Example/1` | `invalid` | `schema_invalid` |
| name unknown, or major version not in this registry | `outside_scope` | `profile_unknown` (notice; error with `--strict`) |

For a profile the verifier does not know, the core checks still run and
decide the record's state. Strict verification fails such a journal, because
its payloads were not checked.
