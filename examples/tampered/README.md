# Tampered examples

Four manipulated copies of [`../transfer-worker.jsonl`](../transfer-worker.jsonl),
one per error class. In each, someone tries to make record #2, a failed
transfer job (`"status":"failed"`, `reason_code` `transfer.source_not_found`),
look like a successful one, or to remove it. The files show what a verifier
reports in each case. Like the other examples they are generated by
`go/internal/vectors`; `expected.json` lists the verdict every verifier must
reach, in the format of `testdata/streams/expected.json`.

| File | What was done | What `verify` reports |
|---|---|---|
| `hash-mismatch.jsonl` | Record #2 edited in the file; hashes left as they were. | `hash_mismatch` on record #2 (content and chain hash). |
| `chain-break.jsonl` | Record #2 edited and re-sealed, so its own hashes are consistent. Record #3 still links to the original. | `chain_break` on record #3. |
| `seq-gap.jsonl` | Record #2 deleted, record #3 re-sealed to link to record #1. | `seq_gap` on the record now at index 2 (seq 3, expected 2). |
| `signature-invalid.jsonl` | Signed journal. Record #2 edited, records #2 and #3 re-sealed, the original signatures copied over. | Without a key: OK. With the producer's public key: `signature_invalid` on records #2 and #3. |

The last file is the case section 6.3 of the specification describes: whoever
controls an unsigned journal can rewrite it so that every hash and link
checks out. A signature binds the chain to a key the editor does not have.
The key here is the published TEST KEY (RFC 8032 test vector 1, in
`testdata/keys/`), so anyone can re-sign with it; real producers use their
own key.

## Try it

In the browser verifier, "load a tampered example" opens
`hash-mismatch.jsonl`. Drop the other files on the page the same way; for
`signature-invalid.jsonl` paste the test public key

```
d75a980182b10ab7d54bfed3c964073a0ee172f3daa62325af021a68f707511a
```

With the CLI, from the repository root:

```bash
trail-evidence verify examples/tampered/hash-mismatch.jsonl
# FAIL: 4 record(s) in 1 stream(s), 2 error(s)
#   error   hash_mismatch     record #2 (line 3, stream "worker-01", seq 2): content_hash mismatch: …
#   error   hash_mismatch     record #2 (line 3, stream "worker-01", seq 2): chain_hash mismatch: …

trail-evidence verify examples/tampered/chain-break.jsonl
# FAIL: 4 record(s) in 1 stream(s), 1 error(s)
#   error   chain_break       record #3 (line 4, stream "worker-01", seq 3): prev_hash … does not match previous chain_hash …

trail-evidence verify examples/tampered/seq-gap.jsonl
# FAIL: 3 record(s) in 1 stream(s), 1 error(s)
#   error   seq_gap           record #2 (line 3, stream "worker-01", seq 3): seq 3, expected 2

trail-evidence verify examples/tampered/signature-invalid.jsonl
# OK: 4 record(s) in 1 stream(s), hash chain intact, 4 signed record(s)

trail-evidence verify examples/tampered/signature-invalid.jsonl \
    --pubkey testdata/keys/test-ed25519.pub --require-signatures
# FAIL: 4 record(s) in 1 stream(s), 2 error(s), 4 signed record(s), 2 signature(s) verified
#   error   signature_invalid record #2 (line 3, stream "worker-01", seq 2): signature does not verify with key ed25519:21fe31dfa154a261
#   error   signature_invalid record #3 (line 4, stream "worker-01", seq 3): signature does not verify with key ed25519:21fe31dfa154a261
```

All four files are valid against the JSON Schema; the manipulation is only
visible in the hashes, links, sequence numbers and signatures.
